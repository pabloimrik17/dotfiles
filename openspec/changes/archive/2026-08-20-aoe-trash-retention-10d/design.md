## Context

See `proposal.md` — Why. AoE's config is generated by a chezmoi `modify_` script (`dot_config/private_agent-of-empires/modify_private_config.toml`) that receives the live file on stdin and overlays **only** the keys in the `MANAGED` list with tomlkit, leaving AoE's runtime writeback intact. Any new knob is one more entry in that list.

Ticket DOT-38 left a blocking unknown open: `aoe settings explain session.trash_retention_days` reported `source: schema default` **even though** `~/.config/agent-of-empires/config.toml` already contained `trash_retention_days = 30`. If AoE were reading the legacy path `~/.agent-of-empires/config.toml`, touching the dotfiles would be pointless. Settled empirically — see D3.

## Goals / Non-Goals

**Goals:**

- Pin retention to 10 days as a managed knob, resistant to default changes and to AoE's writeback.
- Close the path unknown with evidence, and leave the `agent-manager` spec describing the real path.

**Non-Goals:**

- No other `[session]` key that falls back to defaults today is managed (`auto_stop_idle_secs`, `snooze_duration_minutes`, …).
- `delete_to_trash` is not touched: sending to the Trash instead of deleting is exactly what makes retention useful.
- Emptying the Trash is not automated from the dotfiles; AoE purges on its own sweep.

## Decisions

### D1. Add to `MANAGED`, do not write the whole `[session]` table

The merge does *check-then-set*: if the on-disk value already matches, it does not touch the node, so `chezmoi diff` stays silent and re-apply is idempotent. Managing the full table would force pinning ~24 keys that AoE expands by default and would turn every AoE release into a diff conflict. Rejected alternative: a `run_once_` calling `aoe settings set` — it introduces a second writer over the same file and breaks the single-source guarantee the `modify_` provides.

### D2. 10 days, not the ticket's 15

DOT-38 asked for 15; the user drops to 10 (decision of this iteration). No technical constraint: the schema accepts any integer, and the only effect is when AoE purges. The ticket has to be updated so it stops contradicting the spec.

### D3. The XDG path is the correct one — fix the spec, not the chezmoi target

AoE ≥ 1.10.1 reads the XDG path in preference to the legacy one. Verified through 1.14.0, the installed version:

- `~/.agent-of-empires/config.toml` (legacy) **does not exist** on the machine.
- `~/.config/agent-of-empires/config.toml` does exist, mode `0600`, managed by the `modify_`.
- `aoe settings explain` on keys we do manage (`session.default_tool`, `updates.update_check_mode`, `session.confirm_delete`, `theme.name`) reports `source: user value` for all of them, with exactly the dotfiles value.

So AoE reads the XDG path and the `modify_` already points at the right place: nothing to relocate. What is wrong is the spec — its **Purpose** line still documents the legacy path. The location requirement itself was repointed in `711fb2a` (#176); `openspec archive` only rewrites `## Requirements`, so Purpose was left behind and has to be edited directly in the baseline.

### D4. The `source: schema default` was a value coincidence, not a path problem

`trash_retention_days` was 30 on disk and the schema default is 30 too, so AoE collapses the candidates and shows only the default — there is no `user value` candidate to display. It is told apart from a read failure precisely by D3: keys whose value differs from the default do show up as `user value`. Corollary that doubles as a test: on moving to 10 (≠ 30) `explain` **must** switch to `source: user value`. If it still said `schema default` after applying, there would indeed be a path problem and this decision would be wrong.

Confirmed: `aoe settings explain session.trash_retention_days` reports `= 10`, `source: user value`, candidates `user value: 10` / `schema default: 30`. The falsifiable test in `tasks.md` 4.3 passes; D3 and D4 hold.

## Risks / Trade-offs

- **The purge is irreversible: on apply, trashed sessions older than 10 days are lost on the next sweep** → this already happened. The change went live in #170 (`e6528ab`), the apply followed, and the live config carries `trash_retention_days = 10` (line 76, mode `0600`, mtime 12 Aug 15:19). The pre-apply Trash review (`tasks.md` 1.1) no longer gates anything.
- **10 days may be too short to recover an abandoned session** → the value is already a managed knob; changing it is editing one line and re-applying.
- **An AoE release renames or resemanticizes the key** → the merge does not fail (tomlkit writes the key all the same), but an orphan key ignored by AoE would remain. The same `explain` used for verification detects it. Not hypothetical: 1.13.0 moved `[app_state]` out of this file into a sibling `state.toml`, which stays unmanaged.
- **The `agent-manager` spec was accumulating drift unnoticed** → this correction brings it up to date, but adds no guardrail preventing a recurrence. Purpose is the specific blind spot: `openspec archive` never touches it.

## Migration Plan

1. Review AoE's Trash and restore whatever is worth keeping.
2. Edit `MANAGED`, `chezmoi diff`, and confirm the only change is the `trash_retention_days` line.
3. `chezmoi apply` and verify with `aoe settings explain`.

Steps 2–3 have landed: the live config carries `trash_retention_days = 10`, `explain` reports `user value` (D4), and `chezmoi diff` on that path is empty from both the real source dir and `--source .`. Step 1's window closed with the apply.

Rollback: removing the entry from `MANAGED` is not enough. The `modify_` only overlays what it declares; delete the entry and the `10` already written stays on disk. Going back means pinning the desired value explicitly in `MANAGED` and re-applying. What has been purged does not come back.

Mac cleanup (mole)

macOS-only TUI cleaner installed via Homebrew. Every invocation is user-initiated — the dotfiles never call mole from any script, hook, or alias. The only commands that cannot touch your data are mole status and the --dry-run variants below; everything else can delete, including mole analyze.

mole analyze can delete. Despite the name, the disk-usage explorer lets you select entries and move them to the Trash on Enter. Its --help lists only -json, so the capability is invisible where you would look for it. For a purely observational view use mole status.
mole clean empties ~/.Trash. The Trash is treated as reclaimable space and is not covered by the built-in whitelist, so a clean deletes it outright — no Finder confirmation. That defeats this machine's deliberate 30-day retention window (run_once_configure-macos-defaults.sh.tmpl) and destroys the safety net behind mole's own "safe" deletes, which move files to the Trash rather than removing them. So one mole clean can make an earlier mole analyze deletion unrecoverable. To exempt it, run mole clean --whitelist and add ~/.Trash: clean_trash() checks the whitelist first and returns early. (An undocumented MOLE_SKIP_TRASH_CLEANUP=1 also works, but is not a supported surface — prefer the whitelist.)
Command Description
mole Launch the interactive TUI menu
mole clean --dry-run Preview cache and log cleanup without deleting
mole purge --dry-run Preview old project artifacts (node_modules, build dirs)
mole analyze Explore disk usage — can move selected items to the Trash on Enter
mole status Monitor system health — the read-only view
mole clean --whitelist Manage protected paths — add ~/.Trash here

beads telemetry (opted out)

The beads plugin declares bd prime hooks with an empty matcher, so bd runs on every session start and compaction in every directory. beads metrics default to on and prime is on its suppressed-notice list, so the consent banner never reaches a hook — the upload would be silent. Chezmoi ships ~/.config/bd/config.yaml with metrics.disabled: true to turn it off (equivalent to bd metrics off, but reproducible on a new machine).

That file is the only place the switch works: beads reads consent from the user-global config alone, so a repository’s .beads/config.yaml can neither disable nor re-enable it. It also carries metrics.endpoint — unused while disabled, but bd writes any missing key back on its next run, which would drift the managed file.

Node version on launch (nvm-aware shim)

A shim named claude at ~/.local/bin/shims/claude sits ahead of the real ~/.local/bin/claude on PATH. It reads the project's .nvmrc (walking up from the launch dir, then a bounded search down), activates that Node by prepending its bin/ to PATH, then execs the real binary. So claude and its subprocesses (Bash tool, hooks, node/bun/npm) run under the project's Node — through every launcher (wsc, wsh, gh-dash, AoE) with nothing new to type.

Behavior Detail
PATH ordering ~/.local/bin/shims must precede ~/.local/bin (set in .zshrc). If bypassed, the shim is skipped and the real claude runs unchanged — no breakage, just no Node selection.
Fast path Installed version → PATH-prepend only (~0.4 ms). Never sources nvm.sh (~0.8 s).
Cold / alias fallback Version not installed yet, or an alias (lts/*, node) → one-time nvm install/ use, then back to the fast path.
No .nvmrc Near-zero-cost passthrough; PATH untouched.
AoE sandbox NVM_DIR is in AoE's [sandbox].environment passthrough so the shim resolves versions from the filesystem inside the sandbox.
